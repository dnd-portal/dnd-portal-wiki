# Runtime Metadata Architecture Audit

Date: 2026-11-22

Status: design audit only. No application redesign was implemented.

## Executive summary

The current runtime registry is a generated browser-safe projection, not the
canonical content registry. That was an important P0 improvement: full spell,
FAQ and canonical page bodies are no longer imported by the shared layout.
However, the projection is still monolithic. The homepage's client node
imports `src/lib/typescript/data/runtime/index.ts`, which materializes every
runtime link entry into a `runtimeLinks` object even though the homepage uses
only a small subset of link, navigation and popup fields.

Measured current size:

- `src/lib/typescript/data/runtime/generated.ts`: 777,368 bytes on disk.
- Browser chunk `D_aPLMlF.js`: 750,093 bytes uncompressed.
- Homepage initial JavaScript: 906,901 bytes across 23 requests in the current
  production-output audit.
- Total client JavaScript: 5,017,968 bytes uncompressed and 1,082,203 bytes
  gzip in the current build audit.
- Production output: 2,123 routes and 90,424,063 HTML bytes.

The recommended design is a hybrid: keep a very small eager navigation
projection for SSR hydration and ordinary anchors, generate route-scoped JSON
for page metadata, and load popup-only summaries on demand. Canonical TypeScript
remains the single build-time source of truth. The smallest safe first step is
to generate and consume a browser-safe `runtime-core` projection containing
only `href`, `title`, `subTitle`, `external` and the minimum image/accessibility
fields, while keeping the current registry as a compatibility fallback during
measurement. This step should be measured before removing any fields or
changing popup behavior.

## Current architecture and dependency graph

```text
canonical data under src/lib/typescript/data/
        |
        +-- scripts/generate-runtime-metadata.mjs
        |       |
        |       +-- runtime/generated.ts
        |       |     runtimeLinkEntries
        |       |     runtimeChildren
        |       |     runtimeSpellBreadcrumbEntries
        |       |
        |       +-- runtime/site-metadata.ts
        |
        +-- route/server/page builders (build-time and SSR)

runtime/generated.ts
        -> runtime/index.ts
             -> Object.fromEntries(runtimeLinkEntries)
             -> runtimeLinks
             -> getRuntimeData / getOptionalRuntimeData
             -> getRuntimeChildren / navigation lookup
             -> spell breadcrumb lookup

runtime/index.ts -> shared client consumers:
  +layout.svelte / currentPage.ts / SEO helpers
  Link.svelte / PageCard.svelte / Breadcrumbs.svelte
  Sidebar.svelte / Navbar.svelte / PopupHost.svelte

runtime/index.ts -> route-local consumers:
  class pages, tools, sitemap and other page-specific components
```

The root layout imports `currentPage.ts`, SEO helpers and shared components.
`Link.svelte`, `PageCard.svelte`, `Breadcrumbs.svelte`, `Sidebar.svelte` and
`PopupHost.svelte` all use runtime metadata for different reasons. The shared
`PopupHost` renders one DOM host and receives the selected link metadata at
interaction time; it no longer embeds popup HTML in every anchor.

The current registry is generated by
`scripts/generate-runtime-metadata.mjs`. It is derived from canonical data and
is therefore not a second authoring source, but the generated value is still
one browser module with all entries and all optional fields present.

## Metadata classification

| Class             | Current fields/records                                                              | Consumers                                             | Browser requirement                                         |
| ----------------- | ----------------------------------------------------------------------------------- | ----------------------------------------------------- | ----------------------------------------------------------- |
| Global            | site metadata, canonical base URL, a small home/site identity                       | SEO, links, structured data                           | Eager, very small                                           |
| Navigation        | path, href, title/label, parent, hidden, icon size, child relationships             | Navbar, Sidebar, Breadcrumbs, current-page resolution | Eager for visible navigation; route-scoped where possible   |
| Link semantics    | external flag, target href, title, subtitle, image href/alt                         | Link, PageCard, anchors                               | Eager for rendered anchors                                  |
| Popup interactive | description, image, display title, subtitle, full URL                               | PopupHost after hover/focus                           | Lazy or compact shared summary                              |
| Route-specific    | long descriptions, SEO title overrides, source metadata, images, page relationships | current page, SEO, route components                   | SSR/prerender route data; client only if hydration needs it |
| Spell breadcrumb  | slug, name, level slug and label                                                    | dynamic spell Breadcrumbs                             | Small route-specific lookup or generated shard              |
| Build-time only   | page bodies, FAQ answers, spell/class/equipment rules, stat blocks, full registries | prerender, search generation, route loaders           | Must not enter shared browser graph                         |

The current `RuntimeLinkMetadata` combines link semantics, popup content,
navigation metadata, SEO descriptions, images and source metadata in one
record. Optional fields avoid rendering every field, but they do not prevent
the generated object and its strings from being shipped in the same module.

## Exact measured size and duplication

Measured from the current production build and generated source:

| Artifact                     |        Size | Interpretation                                     |
| ---------------------------- | ----------: | -------------------------------------------------- |
| `runtime/generated.ts`       |   777,368 B | source projection, including all serialized values |
| `D_aPLMlF.js`                |   750,093 B | browser runtime metadata chunk                     |
| Initial homepage JavaScript  |   906,901 B | all initial client requests, not only metadata     |
| Total client JavaScript      | 5,017,968 B | all generated client chunks                        |
| Total client JavaScript gzip | 1,082,203 B | all generated client chunks                        |

The pre-live crawler indexes 842 runtime link entries and 821 page entries in
the current build. The runtime module also contains child/navigation data and
spell breadcrumb entries. The exact byte split between those arrays cannot be
reliably inferred from the minified chunk without changing the generator to
emit separate artifacts; this audit deliberately does not modify it.

There are three kinds of duplication to distinguish:

1. Canonical data is transformed into runtime metadata at build time. This is
   intentional projection, not duplicate authoring.
2. The browser receives metadata that different consumers do not all need.
   A popup description, navigation parent and route SEO fields share one
   eager record. This is avoidable packaging duplication.
3. Prerendered HTML contains visible page content while the browser receives
   metadata for hydration and interaction. This is necessary for static SEO,
   accessibility and JS-disabled navigation; removing HTML is not the right
   optimization.

## Component field-use audit

### `Link.svelte`

Needs `href`, `external`, `title`, `img.href`, optional navigation icon size,
and popup data when it opens a popup. It does not need route bodies, FAQ
content or full image/source collections. Its type import of `LinkPath` must
remain type-only so canonical values cannot leak into the client graph.

### `PageCard.svelte`

Needs the same anchor fields plus card label/subtitle, icon/image data and
limited descriptions. It is rendered repeatedly on the homepage, so it is a
high-value consumer for a compact projection.

### `Breadcrumbs.svelte` and `currentPage.ts`

Need path-to-href/title/label relationships and the dynamic spell breadcrumb
tuple. They do not need popup descriptions or complete image/source metadata
for every route. Back navigation currently calls `getRuntimeData` to resolve
the href.

### `Sidebar.svelte` and `Navbar.svelte`

Need navigation parents, labels, hidden state, child paths, icon sizing,
current-route hrefs and selected link titles. The Homebrew dual-navigation
paths must remain distinct: active state is an exact URL/context decision, not
just a shared content ID.

### `PopupHost.svelte`

Needs only the selected link's popup mode, title, subtitle, image and short
description while a popup is visible. It is a strong candidate for a lazy
popup-summary lookup, but the fallback must preserve hover, focus, touch,
reduced-motion behavior and navigation when JavaScript fails.

### SEO and route components

SEO generation and route components may need richer metadata or canonical data
during prerendering. Those consumers should remain server/build-time or route
local. They must not define the root layout's browser dependency boundary.

### Search

Navbar search already lazy-loads its generated index after a two-character
query. Search index data must remain separate from runtime navigation metadata;
putting the full search registry into a new eager runtime module would only
move the problem.

## Architectural alternatives

| Option                                        | Initial JS                                              |                              Requests | Static hosting | Complexity  | Main risks                                                                                   |
| --------------------------------------------- | ------------------------------------------------------- | ------------------------------------: | -------------- | ----------- | -------------------------------------------------------------------------------------------- |
| Modular tree-shakable TypeScript              | Potentially smaller if modules are truly value-isolated |                                   Low | Excellent      | Medium      | barrels, dynamic lookups and object construction can defeat tree-shaking; duplicated imports |
| Route-specific generated JSON                 | Very small initial JS; exact route payloads             | Higher, unless embedded or prefetched | Excellent      | High        | extra requests, popup latency, cache/versioning, hydration and JS-disabled fallback          |
| Hybrid projection + lazy shards (recommended) | Small eager core; popup/route data deferred             |            Moderate and demand-driven | Excellent      | Medium-high | boundary design, fallback paths, stale shard/version mismatches                              |

### Option 1: modular TypeScript

Generate separate modules such as `navigation.ts`, `link-core.ts`,
`popup-summary.ts` and `spell-breadcrumbs.ts`. This preserves the current
import style and avoids network requests, but Vite can still merge modules or
retain a large object if a generic lookup imports every module. It requires
import-graph tests and measured chunks; naming files alone is not enough.

### Option 2: route-specific JSON

Generate `/ _data /routes/<route-key>.json`-style static files and fetch only
the current route or popup target. This gives the strongest theoretical
initial-JS reduction, but increases requests and introduces failure states on
hover/focus. SSR HTML and ordinary anchors can remain complete, but interactive
popup content must have a graceful loading/failure state.

### Option 3: hybrid

Keep a compact eager index for visible navigation and anchor semantics. Generate
separate, content-addressed or build-versioned shards for popup summaries and
route-specific optional metadata. Load a popup shard only on interaction and
route metadata only when a component needs it. This maintains static hosting,
preserves JS-disabled links and limits requests to interactions while removing
fields that are currently shipped to every page.

## Recommended architecture

### Directory structure

```text
src/lib/typescript/data/runtime/
  core.ts                 # tiny site/global identity and path primitives
  navigation.ts           # eager labels, hrefs, parent/child relationships
  spell-breadcrumbs.ts    # compact dynamic spell tuples
  popup-summary.ts        # generated type/loader contract, not eager content
  route-metadata.ts       # route-local optional metadata contract
  index.ts                # compatibility facade with explicit boundaries
static/_data/runtime/
  navigation.json        # only if measured JSON is smaller than TS
  popup/<stable-key>.json # lazy summaries, generated from canonical data
  route/<stable-key>.json # optional route metadata shards
```

The exact TS-versus-JSON choice for each artifact should be made from a build
measurement. The canonical data remains under `src/lib/typescript/data/` and
the generator remains the only producer.

### Import boundaries

- `+layout.svelte`, `currentPage.ts`, `Link.svelte`, `Breadcrumbs.svelte`,
  `Sidebar.svelte` and `Navbar.svelte` may import only `runtime/core` and the
  measured navigation projection.
- `PopupHost.svelte` may import the popup loader contract but must not import
  canonical barrels or the full generated registry.
- Search imports only the generated search index when a search is initiated.
- Route components may import route-specific metadata or canonical data only
  when they prerender/render that route.
- SEO helpers use a small route metadata input during SSR; browser shared code
  must not import canonical value barrels.
- Generator scripts may import canonical data; browser modules must not.

### Data flow

```text
canonical TypeScript
  -> generator validates one source of truth
  -> eager navigation projection -> SSR HTML + shared anchors/sidebar
  -> route metadata projection -> prerendered route and optional hydration
  -> popup summary projection -> lazy interaction lookup
  -> search projection -> lazy search interaction
```

The server/prerender path can use canonical data directly. The browser should
receive the smallest serialized projection that is required to hydrate or
interact with the current page.

### Estimated benefits

These are estimates until a prototype is built and measured:

- Removing popup/SEO/source/image fields from the eager projection could reduce
  the 750 KB runtime chunk substantially; the exact reduction is unknown
  because fields are serialized together today.
- A homepage-specific navigation/core projection could plausibly fit well
  below the current 750 KB chunk, but no unmeasured numeric target should be
  treated as a budget.
- Lazy popup and route shards can trade a small interaction request for lower
  initial parse/evaluation and transfer. First interaction latency must be
  measured on mobile.
- Total site JavaScript may not fall if route data is only moved into lazy
  assets; the success criterion is initial homepage dependency closure and
  main-thread cost, not merely chunk renaming.

## Migration strategy

1. **Inventory and contract tests.** Add a generator report that counts each
   field and records which projection contains it. Add a root-layout import
   boundary test before changing runtime behavior.
2. **Smallest safe first step.** Generate a compact `runtime-core` or
   `navigation` artifact containing only anchor and navigation fields, but keep
   the existing facade available for non-root consumers. Switch one low-risk
   shared consumer, preferably `Link.svelte`, behind an equivalent lookup and
   compare HTML, route, popup and chunk output.
3. **Measure the boundary.** Build and inspect actual browser requests, initial
   JS bytes, gzip, parse/evaluation and root dependency closure. Do not proceed
   if the old registry remains in the homepage initial graph.
4. **Move breadcrumbs/sidebar/current-page.** Preserve exact URL matching and
   both ordinary and Homebrew collection URLs. Test route-specific breadcrumbs
   before removing old lookups.
5. **Extract popup summaries.** Generate lazy summaries or an interaction
   shard. Keep a compact SSR/HTML fallback and make failed loads non-blocking
   to the anchor.
6. **Move route-only metadata.** Only after the shared graph is clean, split
   route SEO/source/image metadata and remove compatibility fields from the
   eager projection.
7. **Delete old facade fields.** Remove compatibility exports only after one
   complete production-output and browser cycle confirms no consumers remain.

## Regression and acceptance tests

Architecture:

- Build the real import graph and fail if root layout transitively imports the
  canonical barrel, spell data, FAQ registry or route-only metadata.
- Fail if `PopupHost` or shared links import canonical values.
- Assert lazy search remains absent from initial homepage requests.
- Detect cycles in the root layout/runtime graph.
- Verify generated projections are deterministic and contain no page bodies,
  FAQ answers, spell rules, class features or stat blocks.

Production output:

- Report route count, total HTML, initial homepage JS request count and bytes,
  gzip sizes, largest chunks and runtime-projection sizes.
- Assert one shared popup host per page and no full popup structure per link.
- Verify semantic anchors, canonical URLs, titles, descriptions, JSON-LD and
  JS-disabled navigation.

Browser and accessibility:

- Homepage, deep spell route, class route and both Homebrew navigation URLs.
- Breadcrumb labels and back navigation.
- Sidebar active state: exactly one context active for duplicated Homebrew
  content URLs.
- Mouse hover, keyboard focus, touch behavior, popup-to-trigger movement and
  popup failure fallback.
- Search initial negative case and post-interaction positive case.
- Hydration/console errors and representative axe checks.

Acceptance criteria for the redesign should be measured relative to the
current 750,093-byte runtime chunk and 906,901-byte homepage initial-JS
baseline. Do not impose a new absolute budget before the first projection
prototype. The redesign must reduce the initial dependency closure without
moving the same registry into another eagerly loaded chunk.

## Playwright `ENOENT` artifact failures

The latest browser run had 8 passed, 2 skipped and 2 failures. The failures
were not page assertions; `browserContext.close` could not open trace and zip
files under `test-results/.playwright-artifacts-*` because the files had
already disappeared. This is consistent with artifact-directory races or
parallel workers sharing cleanup state, not a runtime metadata failure.

It is a separate test-infrastructure issue. It should be fixed independently
by checking Playwright reporter/output configuration, worker isolation and
whether a cleanup process or concurrent run removes `test-results` while a
context is closing. Do not “fix” it by weakening popup, accessibility or
metadata assertions. Generated `test-results/`, `playwright-report/` and
temporary Lighthouse directories remain local-only and must stay out of Git.

## Recommendation

Adopt the hybrid projection architecture. The smallest safe first
implementation is a generator-only `runtime-core`/navigation projection plus
an import-graph and size report, followed by switching `Link.svelte` in one
measured slice. Do not remove the existing registry or change popup loading in
that first step. This limits rollback scope while proving whether the proposed
boundary actually removes `D_aPLMlF.js` from the homepage graph.

## Phase 1 implementation result (2026-11-22)

### Changed files

- `scripts/generate-runtime-metadata.mjs` now also generates
  `src/lib/typescript/data/runtime/core.ts`.
- `src/lib/typescript/data/runtime/core.ts` is a generated projection
  containing path, href, external flag, title, subtitle, description, image
  href/alt and optional icon size, plus an independent canonical-href helper.
- `src/lib/svelte/components/Link.svelte` now consumes `runtime/core.ts` and
  no longer imports `runtime/index.ts` or `currentPage.ts`.
- `src/lib/tests/runtime-core.test.ts` covers href preservation, external and
  internal URL normalization, Homebrew route identity, popup fields and
  missing metadata.
- `scripts/bundle-boundaries.test.mjs` now asserts the Link boundary.

The projection is generated from the existing canonical data. No manually
maintained route or metadata list was added, and PopupHost's event payload and
all Link props remain unchanged.

### Measured result

The phase establishes a source boundary for `Link.svelte`, but it does not yet
reduce the homepage dependency closure. The existing root layout still imports
`D_aPLMlF.js` through `currentPage.ts` and other shared consumers, so the new
projection is loaded in addition to the old registry.

| ---------------------------- | ------------------: | ------------: | --------------- |

| Generated runtime core       |                   — |     413,370 B | New eager chunk |
| Homepage initial JavaScript  |           906,901 B |   1,309,652 B | **+402,751 B**  |
| Homepage initial JS requests |                  23 |            25 | +2              |

The real browser trace confirmed the old chunk remains in the homepage
requests. The initial JS list includes both `D_aPLMlF.js` and the new
`dz8uSVDW.js` core chunk. This phase must not be described as a performance
improvement. It is an architectural boundary with a short-term regression
because the next importer migration has not happened.

### Remaining eager importers

The old registry remains reachable from the root through:

- `src/routes/+layout.svelte` -> `currentPage.ts` -> `runtime/index.ts`;
- `src/routes/+layout.svelte` -> SEO/page helpers -> `runtime/index.ts`;
- shared `Breadcrumbs.svelte`, `Sidebar.svelte`, `Navbar.svelte` and
  `PopupHost.svelte` imports or type/value paths;
- other shared components such as `PageCard.svelte` rendered by the homepage.

`Link.svelte` is no longer an importer of the old runtime module, but it cannot
remove the old chunk while these root consumers remain. The new core is also
not small enough to justify shipping alongside the old registry: its 413,370
bytes still cover all 842 entries, although only Link/popup fields are kept
per entry.

### Decision and next phase

The code is functionally type-checked and unit-tested, but the decision
criterion “reduce unnecessary global JavaScript dependencies” is not met. The
smallest safe next migration is to move the root-layout `currentPage.ts`
lookup to a projection that is not built on `runtime/index.ts`, while
preserving the current facade for route-local consumers. That migration should
happen before retaining the generated core as an eager Link dependency.

If every phase must be performance-neutral, this phase should be reverted and
the root boundary and Link boundary implemented together. It must not be
merged as a performance win in its current form.

## Phase 1B decision (2026-11-22)

The Phase 1 implementation described above was reverted during the Phase 1B
review. The old runtime chunk remained eager through `currentPage.ts`, SEO and
other shared consumers, while `Link.svelte` added a second 413,370-byte
projection. This failed the production budget and increased initial homepage
JavaScript by 402,751 bytes. The generated core file, Link migration, related
boundary assertion and runtime-core unit test are no longer present in the
working tree. All unrelated pre-existing user changes were preserved.

No safe complete migration boundary could be identified without migrating
`currentPage.ts`, Breadcrumbs, Sidebar, Navbar, PopupHost, PageCard and SEO as
a coordinated change. The next implementation should therefore migrate that
shared boundary together, or introduce route-specific current-page data first;
it must not ship a second eager registry alongside `runtime/index.ts`.
